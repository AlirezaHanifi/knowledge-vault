Escalating failure handling

The book’s ideal strategy first asks whether a failure is unambiguously application-level. If so, the application compensates (backward recovery). Otherwise the platform assumes the mildest failure first: transient (retry immediately), then intermittent (retry with backoff), then permanent (suspend, repair, resume). Only then is the failure handed to the application, and if compensation fails, to people.

    What to notice

    • A transient failure (a router restart) is fixed by the very first retry.
    • An intermittent failure (a stale routing table) survives the immediate retry and a few backoff retries, then clears by itself: autorepair after a delay.
    • A permanent failure (an expired certificate) never clears by itself. Suspending the process, letting an operator install a certificate and resuming is what gets the charge through.
    • InsufficientFunds is meaningless to the platform, so retries are pointless. The application compensates the steps already done, and if that refund fails too, operators take over.
