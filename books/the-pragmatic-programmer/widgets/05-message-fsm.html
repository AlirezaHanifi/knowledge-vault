Table-driven state machines

A finite state machine is just a table: for each state and event, the next state and optionally an action. The code that runs it is one line: look up TRANSITIONS[state][event], falling back to a default entry or to :error.

Illustrates “Finite State Machines” in Topic 29, Juggling the Real World (pp. 240–246): the multipart message parser (pp. 241–243) and the string extractor with actions (pp. 243–245). The states, events and actions are the book’s; the stepping display is the vault’s. Implementation is the vault’s own.

    What to notice

    • All the behaviour lives in the table. Adding a state or an event is a new row, not a new branch of nested if statements.
    • The backslash state (copy_next_char) copies the next character whatever it is, so an escaped quote doesn’t end the string.
    • The multipart parser has no default row: any event the table doesn’t list, such as data before a header or a second trailer, sends it to :error.
