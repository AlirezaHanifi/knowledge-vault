Saboteurs and state coverage

To test your tests, cause the bug deliberately and check that the tests complain. And remember that running every line isn’t enough: what matters is the states a program can be in, not the lines it has.

Illustrates “Testing the Tests” and “Testing Thoroughly” in Topic 51, Pragmatic Starter Kit (pp. 457–458, Tips 92–93), including the book’s a / (a + b) function with a and b from 0 to 999. The clamp function, its mutants and its tests are the vault’s. Implementation is the vault’s own.

clamp(x, lo, hi): if x < lo return lo; if x > hi return hi; return x

test(a, b) = a / (a + b), with a, b in 0–999

    What to notice

    • A single happy-path test passes, and lets six of the seven real planted bugs survive. A green suite says little about whether the alarms work.
    • Tests just outside the range (11 and −1) kill the off-by-one mutants that move a boundary; tests far outside (42 and −3) miss them. Some mutants, such as < becoming <=, are equivalent: they behave the same, so no test can catch them.
    • One line, a million states: a / (a + b) fails only when a = b = 0. Covering the line takes one test; finding that state by chance takes about a million.
