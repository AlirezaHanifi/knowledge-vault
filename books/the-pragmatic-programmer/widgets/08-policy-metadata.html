Policy as code or as data

“Only an employee’s supervisors and the personnel department may view that employee’s records” is business policy dressed as a requirement. Code it as an if and every policy change is a code change. State it as “only authorized users may access a record”, and policy becomes metadata in an access-control table.

Illustrates “Requirements vs. Policy” in Topic 45, The Requirements Pit (pp. 411–412, Tip 79). The sequence of policy changes, the roles and the table layout are the vault’s. Implementation is the vault’s own.

      What to notice
      
  
        
    
      • Both versions give the same answers. The difference is what changing them costs: an edit, a review and a redeploy for code, against a row edit for data.
        • 
    
      • The general mechanism is built once. After that, each new policy is an example of the kind of thing it supports, which is the book’s advice: implement the general case.
        • 
    
      • Policy changes keep coming. The book says they will. A hard-coded check grows a new branch for each one, and old branches are rarely removed.
