Bin packing vs partial commits

Some bulk APIs can partially commit: part of a request lands and the rest fails. If 10:20 lands and 10:00 and 10:10 are retried, the consumer reads them out of order. The Bin Pack Orderer sorts records and packs them so that each bin holds at most one record per key. It sends bins one after another and finishes each bin's retries before starting the next.

    What to notice

    • Naive bulk requests reorder keys. Whenever an early record fails and a later one of the same key succeeds, the retry lands after it.
    • Bins can't reorder. A bin never holds two records of the same key, and bin k+1 waits until bin k is fully written.
    • Compare the request counts. One record per request is also ordered, but it costs a request per record. Bins need about as many requests as the longest key has records, plus retries.
    • Set the failure chance to 0. All three strategies are then correct, and bulk wins. Ordering only breaks under partial failures.
