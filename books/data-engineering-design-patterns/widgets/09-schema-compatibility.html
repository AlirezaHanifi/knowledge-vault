Schema compatibility checker

A schema registry accepts a new version only if readers can still handle it. Backward compatibility means a new reader can read old data. Forward means an old reader can read new data. Full means both. Transitive modes check against every earlier version, not just the previous one.

Illustrates “Pattern: Schema Compatibility Enforcer” (pp. 284–290). The presets are the book's Order v0 → v1 → v2 (pp. 287–288) and its forward-compatible Visit schema with a producer that drops visit_id (p. 289). The reading rule is Avro-like: a reader's field that's missing from the data needs a default, and extra fields in the data are ignored. Types never change here. Implementation is the vault's own.

    • Order preset, backward mode. v2 can read v1 data, where the default fills amount, but not v0 data. Tick Transitive and v2 is rejected (pp. 287–288).
      • 
    
    • Visit preset, forward mode. An old reader needs visit_id, which has no default, so registering the version without it fails with READER_FIELD_MISSING_DEFAULT_VALUE (p. 289).
      • 
    
    • Mirror-image rules. Backward allows deleting fields and adding optional ones. Forward allows adding fields and deleting optional ones (Table 9-1).
      • 
    
    • A rename is a delete plus an add. Under full compatibility it needs the Schema Migrator's grace period.
