Single vs concurrent runner

An hourly pipeline is fine while each run takes less than an hour. When runs take longer, a Single Runner queues them, and every delivery is later than the one before it. A Concurrent Runner starts the next run while earlier ones are still going. That only works when runs don't depend on each other.

Illustrates “Pattern: Single Runner” and “Pattern: Concurrent Runner” (pp. 191–195). The book's example is an hourly flow whose 30-minute runs grow to 1.5 hours, which makes delays accumulate (p. 192). Here every run has the same duration, and a run starts as soon as a slot is free. Shared state between concurrent runs (p. 194) isn't simulated. Implementation is the vault's own.

    What to notice

    • Stretch the runs to 90 minutes with concurrency 1. Each delivery is 30 minutes later than the previous one. After 12 runs, the last is 5.5 hours late.
    • Raise the concurrency to 2. The delay disappears, because two 90-minute runs fit into two hourly slots.
    • Concurrency isn't free. It's only safe if runs are independent. Incremental logic such as the Incremental Sessionizer needs one run at a time, and backfills can then only be sequential (p. 192).
