Merger vs Stateful Merger

A MERGE upserts each increment into the latest table. That is idempotent for a single rerun. During a backfill, though, the replay starts from today's table, so consumers see rows that didn't exist yet at the replayed time. The Stateful Merger records which table version each run produced. Before a backfill it restores the version of the previous run.

Illustrates “Pattern: Merger” and “Pattern: Stateful Merger” (pp. 89–100). The increments and expected outputs are those of Tables 4-1 and 4-2 (p. 92): A at 07:00; A–U and B at 08:00; B–D and C at 09:00; M, N and O at 10:00. U is an update and D a soft delete. The restore rule follows pp. 95–96: no previous version → truncate; previous version = latest → normal run; otherwise restore. As in Tables 4-4 and 4-5, only MERGE commits get version numbers, so restores aren't counted. Implementation is the vault's own.

    What to notice

    • Run the four hours, then backfill from 08:00 with the plain Merger. After the 08:00 rerun the table holds A–U, B, C, M, N and O, as in Table 4-2. C, M, N and O didn't exist at 08:00.
    • Switch to the Stateful Merger and repeat. The 08:00 rerun finds version 1 for 07:00, which differs from the latest version, 4. It restores version 1 first, so consumers see exactly Table 4-1's rows.
    • Backfill from 07:00. There is no earlier run, so the table is truncated before the merge (p. 96).
    • The rest of the replay needs no restores. Each later run finds that its predecessor's new version is the latest one.
