Chapter 8 · Advanced concurrency control

Swap or lock

Three threads each increment a counter of database accesses. Unprotected, a context switch between read and write loses updates. A mutex makes the others wait. An atom lets everyone compute, then commits with an atomic compare-and-set and retries if the value changed meanwhile.

Illustrates sections 8.1–8.2 (listings 8.1–8.4, figure 8.2, pp. 164–170): the counter, the mutex version, and swap built on atomicCompareAndSet. The threads are simulated by a seeded scheduler that picks which one takes the next step. Implementation is the vault’s own.

    What to notice

    • Unprotected increments lose updates: two threads read the same value, both add one, and one write overwrites the other.
    • A mutex is correct but makes threads wait, and the book’s war stories show how a lock not released, or released in the wrong order, deadlocks.
    • An atom never waits and never loses an update. A failed compare-and-set means another thread succeeded, so “there is always a winner”; the loser just recomputes.
