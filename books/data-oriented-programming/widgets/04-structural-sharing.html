Structural sharing

An immutable “set” never changes the data it receives. It creates new maps only along the path to the change and shares every other part with the previous version. That makes versions cheap, but only as long as nobody mutates shared data behind its back.

Illustrates sections 4.2–4.4 (pp. 74–83): the publication-year change of figure 4.4, Dave’s setImmutable (listing 4.4) and the shared-array mutation of listing 4.5. The library data is the vault’s small sample. Implementation is the vault’s own.

        What to notice

        • Only the maps on the path are new: the library, the catalog, booksByIsbn and the Watchmen record. userManagement, authorsById and the book’s arrays are the very same objects in both versions.
        • The previous version is untouched: it still says 1987. Both versions exist side by side at almost no cost.
        • A native setter breaks the deal. Changing authorIds[1] in the previous version changes the next one too, because the array is shared. That is why native mutation is forbidden, and why persistent data structures exist.
