Commit and undo

A DOP mutation has two phases. The calculation is a pure function that returns the next version or throws. The commit is common to all mutations: it validates the next version and moves the system state forward. Keeping the old references makes undo trivial.

Illustrates sections 4.5–4.7 (listings 4.7–4.10, pp. 83–89): System, SystemState, whole-system validation at commit, and undo with previousSystemData. The member names, the invalid lending example as data and the stack option are the vault’s (the book mentions a stack on pp. 88–89). Implementation is the vault’s own.

      What to notice

      • The calculation can fail on its own: adding a member who already exists throws “Member already exists.” and nothing is committed.
      • The commit can reject what the calculation produced: a lending without the copy marked lent is an invalid system state, caught once for the whole system instead of in each class.
      • One previous reference allows one undo. Undo twice and you stay where you are; with a stack of references, every version can be restored. Structural sharing keeps them cheap.
