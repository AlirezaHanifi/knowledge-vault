Split code from data

In Theo’s OOP design, Member sits in five relations: two about its data, three about its code. Split it into MemberData and MemberCode and each half is simpler. Split every class and the diagram falls into a data part and a code part you can understand separately.

Illustrates section 1.2.1, Many relations between classes (figures 1.10–1.13, pp. 14–16). The relations are taken from the class roles on pp. 9–12; the layout is the vault’s. Data relations are composition and association; code relations are usage and inheritance. Implementation is the vault’s own.

      What to notice

      • Member’s five relations become two plus three: MemberData keeps “Library has many” and “has many BookLending”; MemberCode keeps “extends User” and the two usages.
      • Splitting every class leaves two independent parts: one with only data entities and data relations, one with only code entities and code relations (figure 1.13).
      • No relation crosses between the parts. That is what lets you understand the data without thinking about the code, and the other way round: the result follows from separating code from data, not from luck.
