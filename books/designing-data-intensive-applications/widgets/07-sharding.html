Sharding and rebalancing

Sharding spreads data and load over many machines. Two questions decide whether it works: how much data has to move when a node joins, and whether the load actually ends up even.

Illustrates “Sharding by Hash of Key” (hash mod N, fixed number of shards, hash-range sharding, consistent hashing; pp. 258–263) and “Skewed Workloads and Relieving Hot Spots” (pp. 263–264). Rendezvous (highest-random-weight) hashing is one of the consistent hashing algorithms the book names. Implementation is the vault’s own.

What to notice

  • Hash mod N moves almost every key when N changes (going from 3 to 4 nodes keeps only about a quarter in place) — far more than the 1/N share the new node needs.
  • Fixed number of shards moves whole shards: the new node steals some shards from each existing node, so only about 1/N of the data moves. Balance is limited by shard granularity — try 16 shards on 12 nodes.
  • Rendezvous hashing also moves ~1/N, but the new node receives individual keys scattered across all old nodes rather than whole shards.

What to notice

  • Key-range sharding + sequential keys (e.g. timestamps): every write lands on the shard holding the newest range — one hot shard, the rest idle. Hashing the key spreads them.
  • A single hot key (a celebrity's post) defeats any hash: all its writes go to one shard. Appending two random digits splits its writes over 100 keys — at the cost of reads that must now fetch and combine all 100.
