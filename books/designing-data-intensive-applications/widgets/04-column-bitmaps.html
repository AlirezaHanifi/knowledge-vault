Column storage and bitmap indexes

A column store keeps each column’s values together, in the same row order. A column with few distinct values becomes one bitmap per value — a bit per row — and those mostly-zero bitmaps run-length encode to almost nothing. Filters then turn into bitwise OR and AND.

Illustrates “Column-Oriented Storage”, “Column compression” and “Sort order in column storage” (pp. 137–141, Figures 4-7 and 4-8, and the two example WHERE clauses on p. 140). The 24 sales rows are the vault’s own toy data; real blocks hold thousands to millions of rows. Implementation is the vault’s own.

Each column is one line: row k is position k in every line. Run-length encoding (right) lists alternating run lengths, starting with zeros — 3,2,19 = 3 zeros, 2 ones, 19 zeros.

Query

product_sk IN (…) — bitwise OR
AND store_sk = … — bitwise AND

What to notice

  • Row k is bit k everywhere. AND-ing a product bitmap with a store bitmap only works because every column keeps the rows in the same order.
  • Sparse bitmaps compress. Each bitmap is mostly zeros; run-length encoding stores a few counts instead of 24 bits.
  • Sorting helps compression. Sort by product_sk and each product’s ones become one contiguous run — the first sort column compresses best (p. 141).
  • Only touched columns are read. The query needs product_sk and store_sk; the other columns never leave disk.
