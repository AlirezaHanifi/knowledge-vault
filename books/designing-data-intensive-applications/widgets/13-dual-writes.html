Dual writes vs a change log

Client 1 sets item X to A; at almost the same moment Client 2 sets it to B. Both values must reach the database and the search index. If each client writes to both systems itself, network delays can deliver the updates in different orders. If the index is derived from the database’s change log, it applies them in the database’s order.

Illustrates “Keeping Systems in Sync” (pp. 501–503, Figure 12-4) and “Combining Specialized Tools by Deriving Data” (pp. 540–544). Network delays are random but seeded; times are in milliseconds. Implementation is the vault’s own.

    What to notice

    • Dual writes fail silently. No write returns an error, yet the two systems end up permanently disagreeing — until some later write happens to overwrite both.
    • A single log fixes the order. The database decides which write came last; every derived system replays its change log in that order, so all of them converge.
    • Deriving is asynchronous. In change-log mode the index lags behind the database: a read from the index just after a write may still see the old value.
    • Partial failure is the other half of the problem. With dual writes, one write can succeed and the other fail; with a log, a failed consumer retries from its offset.
