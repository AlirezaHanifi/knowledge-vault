Isolation levels, one interleaving at a time

Race conditions between transactions only show up under particular interleavings. Pick an anomaly, pick an isolation level, and step through the same interleaving to see whether the database lets it through, blocks a transaction, or aborts one.

Scenarios follow the book’s examples: the unread-counter dirty read (Figure 8-2, p. 285), Aaliyah’s two $500 accounts (read skew, Figure 8-6, p. 294), the counter incremented from 42 (lost update, Figure 8-1, p. 282), and Aaliyah and Bryce going off call (write skew, pp. 303–304). The engine is a simplified MVCC model written for the vault: row-level write locks at every level; snapshot isolation optionally aborts on concurrent updates (as PostgreSQL’s repeatable read does, p. 301); “serializable” is a simplified SSI that aborts a committing read-write transaction if anything it read was overwritten by a concurrent commit.

What to notice

  • All levels here prevent dirty writes: a second writer to the same row waits for the first to commit or abort (shown in amber).
  • Read committed lets each statement see the latest committed data, so two reads in one transaction can see different moments — read skew.
  • Snapshot isolation reads from a consistent snapshot. Whether it stops lost updates depends on the implementation — toggle the checkbox.
  • Write skew slips through snapshot isolation because the two transactions write different rows; there is no write conflict to detect. Only serializable isolation catches it — by aborting one transaction, which the application must retry.
