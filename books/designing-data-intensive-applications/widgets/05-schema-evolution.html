مقایسه‌ی writer's schema و reader's schema

قالب Avro با دو schema decode می‌کند: writer's schema، که رکورد با آن encode شده، و reader's schema، که اپلیکیشن انتظارش را دارد. فیلدها با اسم جفت می‌شوند؛ فیلدی که فقط نویسنده دارد نادیده گرفته می‌شود و فیلدی که فقط خواننده دارد default خواننده را می‌گیرد. این‌که این تطبیق در هر دو جهت کار کند، forward و backward compatibility را تعیین می‌کند.

برای بخش «قالب Avro»، از جمله writer's schema و reader's schema و قاعده‌های تکامل schema در صص. ۱۷۲–۱۷۵، با schema و رکورد نمونه‌ی کتاب، یعنی Person با Martin و 1337 و daydreaming و hacking. قاعده‌های شماره‌ی tag در Protocol Buffers از ص. ۱۷۱ در نکته‌ها آمده. پیاده‌سازی مال خود vault است.

نتیجه

به چه چیزی دقت کنید

  • مقدار default است که تغییر را بی‌خطر می‌کند. فقط فیلدهایی را اضافه یا حذف کنید که default دارند، تا هر دو جهت کار کنند (ص. ۱۷۵).
  • اضافه کردن بدون default backward compatibility را می‌شکند: کد جدید وقتی رکورد قدیم را می‌خواند چیزی برای گذاشتن در فیلد ندارد.
  • حذف بدون default forward compatibility را می‌شکند: کد قدیم وقتی رکورد جدید را می‌خواند فیلدی را که لازم دارد پیدا نمی‌کند.
  • تغییر نام با alias سازگار backward است اما forward نه؛ خواننده‌های قدیم اسم تازه را نمی‌شناسند.
  • قالب Protocol Buffers به جای اسم از شماره‌ی tag استفاده می‌کند: اسم‌ها آزادانه عوض می‌شوند، هیچ tagی دوباره به کار نمی‌رود و tagهای ناشناخته رد می‌شوند (ص. ۱۷۱).
