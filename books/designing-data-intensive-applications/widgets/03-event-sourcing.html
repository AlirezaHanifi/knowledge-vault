Event sourcing and CQRS

Write in the form that is easiest to write — an append-only log of immutable events — and derive whatever read-optimized views you need from it. Commands are validated first; only valid ones become events, named in the past tense. Because the views are derived, you can delete one, fix its code, and rebuild it by replaying the log.

      What to notice

      • Commands vs events. A booking larger than the free seats is rejected before anything is logged; a view consuming the log may never reject an event.
      • Intent is preserved. “BookingCancelled” says why rows changed, instead of a set of anonymous updates to several tables.
      • Views are reproducible. The dashboard’s v1 code forgets cancellations. Switch to v2 and replay: the same events in the same order produce the corrected view.
      • Time travel. Replaying only the first k events shows the state at any past point; order matters, unlike rows in a fact table.
