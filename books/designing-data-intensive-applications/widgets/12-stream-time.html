مفهوم event time، processing time و late event

هر رویداد زمان رخ دادنش را دارد، یعنی event time، اما دیرتر به پردازش‌کننده‌ی stream می‌رسد، یعنی processing time. window بر اساس زمان رسیدن آسان است اما وقتی latencyها متغیرند غلط است؛ window بر اساس event time درست است اما تصمیمی را تحمیل می‌کند: یک window کی کامل است، و با رویدادهایی که بعد از آن می‌رسند چه می‌شود؟

برای بخش «استدلال درباره‌ی زمان» در صص. ۵۱۸–۵۲۳: event time در برابر processing time، عددهای ساختگی processing time در شکل ۱۲-۸، مدیریت رویدادهای دیررس، یعنی نادیده گرفتن یا انتشار اصلاحیه در ص. ۵۲۰، و tumbling window در ص. ۵۲۲. مدل رسیدن رویدادها تصویرسازی خود vault است.

    به چه چیزی دقت کنید

    • مفهوم window بر اساس processing time با latency کج می‌شود: ستون «بر اساس رسیدن» رویدادها را در windowی می‌شمارد که اتفاقاً در آن رسیده‌اند، نه windowی که به آن تعلق دارند. latency را بالا ببرید یا رویدادهای آفلاین را بیشتر کنید تا دو ستون از هم دور شوند.
    • صبر بیشتر late eventها را کم می‌کند اما نتیجه را دیر می‌کند. مهلت بسته شدن بده‌بستان بین کامل بودن و latency است؛ وقتی بعضی دستگاه‌ها مدت زیادی آفلاین‌اند، هیچ تنظیمی هر دو را نمی‌دهد.
    • نادیده گرفتن late eventها شمارش‌ها را برای همیشه غلط می‌گذارد؛ تعداد دورریخته‌ها را دنبال کنید. انتشار اصلاحیه درستشان می‌کند، اما consumerهای downstreamی باید با تغییر مقدار یک window بعد از اولین انتشار کنار بیایند.
