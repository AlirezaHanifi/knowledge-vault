Event time, processing time, and stragglers

An event carries the time it happened (event time), but reaches the stream processor later (processing time). Windowing by arrival time is easy but wrong when delays vary; windowing by event time is right but forces a decision: when is a window complete, and what happens to events that arrive after that?

    What to notice

    • Processing-time windows are distorted by delay: the “by arrival” column counts events in the window they happened to arrive in, not the one they belong to. Raise the delay or add a backlog burst and the two columns diverge.
    • Waiting longer reduces stragglers but delays results. The grace period is the trade-off between completeness and latency — there is no setting that gives both when some devices are offline for a long time.
    • Ignoring stragglers leaves permanently wrong counts (track how many you drop). Publishing corrections fixes them, but downstream consumers must handle a window’s value changing after it was first emitted.

    Vault note: the book describes a processor emitting a special message meaning “no more events earlier than t will arrive”. Stream frameworks commonly call this a watermark; the grace-period rule used here is the simplest such heuristic.
