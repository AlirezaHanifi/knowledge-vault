Concurrent writes: siblings vs last write wins

Two writes are concurrent when neither knew about the other. The server can tell from version numbers: a write carries the version it was based on, overwrites everything up to that version, and keeps anything newer as a sibling for the client to merge. Last write wins skips all that — and silently drops items.

Illustrates “Last write wins”, “The happens-before relation and concurrency” and “Capturing the happens-before relationship” (pp. 237–242, Figures 6-15 and 6-16): the book’s five cart writes on a single replica. With several replicas the same idea needs a version vector (p. 242). Implementation is the vault’s own.

      What to notice

      • Version numbers capture “knew about”. Client 1 writes [milk, flour] based on version 1: it replaces [milk] but cannot replace [eggs], which it never saw — so [eggs] stays as a sibling.
      • Clients merge siblings. Each write merges everything the client last received, so nothing is lost even though the clients are never fully up to date.
      • Last write wins is not “latest”. Switch modes and replay: each write overwrites the cart, and items added by the other client vanish without an error.
      • Try your own order. Add items directly from either client; a client that never read writes with version 0, concurrent with everything.
