Queueing, overload, and retry storms

A server can only work on one request at a time, so every request that arrives while it is busy waits in a queue. Near capacity those waits dominate the response time — and if clients retry the requests that time out, a short spike can leave the system stuck in overload.

Illustrates “Describing Performance” (pp. 37–39: Figure 2-3, queueing delay, head-of-line blocking) and the sidebar “When an Overloaded System Won’t Recover” (p. 38: retry storms, metastable failure, backoff, load shedding). A single first-come-first-served server with random (seeded) arrivals and service times of 10 ms, with an occasional 100 ms slow request; clients time out after 1 s. What to notice

  • The knee. Response time stays flat at low load and climbs steeply past ~80% of capacity — not because each request gets slower, but because each one waits longer behind others.
  • Head-of-line blocking. Raise the share of slow requests: a few 100 ms requests hold up the fast ones queued behind them, so p99 grows much faster than the median.
  • Metastable failure. At 85% load with immediate retries, the spike ends at 9 s but the queue never drains: timed-out requests are still served (wasted work) while their retries add even more load.
  • The fixes from the book. Backoff with jitter cuts the number of requests sent, but on its own it does not end this storm: the server still works through requests whose clients have given up. Add load shedding and the queue stays short, so accepted requests finish in time and the system recovers.
