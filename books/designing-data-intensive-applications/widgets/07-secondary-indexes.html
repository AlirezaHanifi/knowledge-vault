Chapter 7 · Sharding

Local vs global secondary indexes

Car listings are sharded by ID. To find red cars you need a secondary index on colour — and it does not map neatly onto the shards. A local index lives beside each shard’s data (cheap writes, every read asks every shard); a global index is sharded by the indexed term (targeted reads, writes may touch other shards).

Illustrates “Sharding and Secondary Indexes”, “Local Secondary Indexes” and “Global Secondary Indexes” (pp. 268–271, Figures 7-9 and 7-10): IDs 0–499 in shard 0 and 500–999 in shard 1, and a global index split at a–r / s–z for colour and a–f / h–z for make. A third shard and the particular cars are the vault’s own. Implementation is the vault’s own.

What to notice

  • Local: scatter/gather reads. Red cars can be on any shard, so a search for all of them asks every shard and combines the results — prone to tail latency, and adding shards doesn’t add query throughput.
  • Local: writes stay on one shard. Adding a listing only touches the shard that holds its ID.
  • Global: one shard per term. color = red reads one index shard for the postings list — but fetching the records themselves still goes to the shards holding those IDs.
  • Global: AND across terms and multi-shard writes. colour and make may live on different index shards; the postings lists must be shipped and intersected, and one new listing can update several index shards.
