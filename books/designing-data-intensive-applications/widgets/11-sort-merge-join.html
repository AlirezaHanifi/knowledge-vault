Shuffle and sort-merge join

To analyse page views by age, a batch job joins activity events with the user database. Mappers key every record by user ID; the shuffle routes each key to one reducer and sorts it; the reducer then sees one user’s record next to that user’s events — no lookups, no network requests.

Illustrates “Shuffling Data” and “Joins and Grouping” (pp. 469–473), after Figures 11-1 to 11-3. The records, the two reducers and the hash function (user number mod 2) are the vault’s own toy choices; implementation is the vault’s own.

    What to notice

    • The shuffle is a distributed sort. Each mapper splits its output by hash of the key, one partition per reducer; each reducer merges the sorted partitions it fetches from every mapper.
    • All records with the same key meet in one place. That is what makes the join local: the reducer needs no database lookups.
    • The secondary sort keeps memory constant. With the user record first, the reducer holds one record at a time. Turn it off and the reducer must buffer a user’s events until the user record turns up.
    • Inputs are never modified. If a reducer failed, it could rerun on the same sorted partitions.
