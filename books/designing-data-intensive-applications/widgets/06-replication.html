Replication lag and quorums

A leader streams its changes to followers, but followers apply them late. Reading from a lagging follower can make your own writes vanish or make time appear to go backward — and promoting a lagging follower after a crash loses writes. Leaderless systems instead read and write overlapping subsets of replicas.

Illustrates “Synchronous Versus Asynchronous Replication” (p. 200), “Handling Node Outages” (p. 204), “Problems with Replication Lag” and “Solutions for Replication Lag” (pp. 209–215), and quorum reads/writes in “Leaderless Replication” (pp. 229–235).     What to notice

    • With random replica routing, a read right after a write often misses it — a read-after-write violation. Route your own reads to the leader to fix it.
    • Two reads in a row can hit followers with different lag, so a later read returns an older value — a monotonic reads violation. Sticky routing (always the same replica) fixes it.
    • Press Leader fails while writes are in flight: the most up-to-date follower is promoted, and writes it never received are lost even though the client was told they succeeded. Make follower 1 synchronous and the acknowledged writes survive — at the price of slower writes.

      What to notice

      • When w + r > n, every read set overlaps the last write set in at least one replica, so the read can return the newest version (it takes the highest version number it sees).
      • Set w = 1, r = 1 with n = 5: reads are fast and available, but most of them are stale.
      • Take nodes down: writes and reads fail outright once fewer than w or r replicas are reachable. Quorums trade availability for the overlap guarantee — and even with the overlap, the book notes edge cases (concurrent writes, partially failed writes, clock-based conflict resolution) where stale values can still appear.
