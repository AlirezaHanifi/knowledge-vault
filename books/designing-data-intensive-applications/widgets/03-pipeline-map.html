فصل ۳ در طول یک pipeline داده

ایده‌های این فصل یک انتخاب یک‌باره نیستند: یک pipeline از چند تای آن‌ها می‌گذرد. یک lens انتخاب کنید، مرحله‌ها را از دیتابیس منبع تا داشبورد طی کنید و ببینید داده کجا شکلش را عوض می‌کند.

کل فصل را، صص. ۶۵–۱۰۸، روی reference stack خود vault نشان می‌دهد، یعنی یک پلتفرم داده‌ی عمومی: دیتابیس relational منبع ← loader ← لایه‌های Bronze و Silver و Gold در یک warehouse ستونی ← notebook، داشبورد و یک API. مرحله‌ها و نمره‌های ۱ تا ۵ ساده‌سازی خود vault است، و پیاده‌سازی هم.

شکل داده در این مرحله

به چه چیزی دقت کنید

  • با lens شکل: داده normalized شروع می‌شود و denormalized تمام می‌شود. هر قدم به جلو سادگی write را با سرعت read عوض می‌کند، و هر جدول denormalized یک derived data است که با تغییر ورودی‌هایش باید rebuild شود.
  • با lens اسکیما: دو سر pipeline، یعنی دیتابیس منبع، جدول‌های Gold و API، schema-on-write هستند و وسطش schema-on-read. لایه‌ی Silver جایی است که شکل قدیم و جدید منبع در SQL با هم آشتی داده می‌شوند.
  • با lens وضعیت یا log: فقط Bronze تاریخچه نگه می‌دارد. همین Silver و Gold را rebuildپذیر می‌کند، و همین دلیل است که چیزی که loader هیچ‌وقت نمی‌بیند، مثل hard delete، در downstream هم هیچ‌وقت درست نمی‌شود.
  • با lens interface: تحلیلگرها SQL باز را پشت یک proxy با محدودیت می‌گیرند و اپلیکیشن‌ها یک API باریک. فراخواننده هرچه کمتر قابل اعتماد باشد، interface باریک‌تر است.
