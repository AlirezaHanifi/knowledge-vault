Exactly once, end to end

A user submits a transfer; it commits, but the response is lost on a weak connection, so they press submit again. To the server and the database that retry is a brand-new request, and every transaction commits. Only an ID created at the client and checked by the database can tell the two apart.

Illustrates “Duplicate suppression”, “Uniquely identifying requests” and “The end-to-end argument” (pp. 563–566, Example 13-2: $11.00 from account 4321 to 1234, guarded by a unique request_id). Lost responses are random (seeded); each client gives up after three attempts. Implementation is the vault’s own.

    What to notice
    
  
      
    
    • Every hop is “reliable” and still wrong. TCP removes duplicate packets and the database runs each transfer atomically, but a user’s retry is a new connection and a new transaction.
      • 
    
    • The fix spans the whole path. Generate the ID in the client (e.g. a hidden form field), carry it through, and let a uniqueness constraint reject the second insert — the whole transaction aborts.
      • 
    
    • The requests table is an event log. Balances could be derived from it downstream, as long as each event is processed exactly once — again using the request ID.
      • 
    
    • The end-to-end argument: lower layers can make problems rarer, but only the endpoints can make the function correct (p. 565).
